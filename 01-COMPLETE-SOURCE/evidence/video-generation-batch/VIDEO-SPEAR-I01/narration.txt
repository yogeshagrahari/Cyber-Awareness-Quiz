Scenario: A message uses your real project name and mentions a current deadline. It asks you to open a shared document and sign in again, but the sender domain differs from the partner’s known domain. Safest response: Option A: Verify the request with the partner using a previously established contact channel, and access the project system independently. Use relationship and workflow context as signals, but authenticate through an independent channel. Option B is unsafe because Changing devices does not make a deceptive link or credential prompt trustworthy. Option C is unsafe because A response goes to the potentially compromised sender and does not independently verify the request. Option D is unsafe because Public or compromised information can make targeted deception convincing; context alone is not authentication. In practice: Pause the sign-in request, contact the partner through known contact details, and report the mismatch to the security team. Key takeaway: Targeted content can be accurate and still fraudulent; independently verify the sender and workflow.
